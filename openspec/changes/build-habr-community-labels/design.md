## Context

Проект содержит только OpenSpec scaffold. Мотивация и границы продукта описаны в proposal.md. Требуется новый клиент и сервер, публичные пользовательские данные и OAuth; поэтому design необходим. Решения последнего обсуждения: GitHub, Chromium и Firefox, панель внутри страницы, красный порог 3/80%, partial только в знаменателе.

## Goals / Non-Goals

**Goals:** единая серверная классификация; одинаковый интерфейс браузеров; защищённая привязка голосов к пользователю; минимальный развёртываемый backend.

**Non-Goals:** отдельные микросервисы, Redis, WebSocket, ML, копирование полного текста статей, неизменяемая история голосов, репутационная модель, автоматическая синхронизация настроек между браузерами.

## Decisions

### Workspace и runtime

pnpm workspace с apps/extension и apps/api. TypeScript в обоих; WXT, React 19 и MV3 в расширении; Fastify, PostgreSQL и Prisma 8 в API. Для Firefox явно выставить manifestVersion: 3, не полагаться на default WXT. Версии фиксируются lockfile при реализации после проверки совместимости. Prisma 8 не заменять молча другой major: сначала проверить доступный релиз, создание схемы, миграцию и запрос к PostgreSQL. Если стек не собирается, сообщить о конкретном блокере до основного кода. Общий пакет не создавать заранее: типы ответов экспортировать из API через type-only imports, без серверного runtime в клиентской сборке.

### Интеграция с Хабром

Content script извлекает положительный числовой article ID из известных ссылок статей, включая company routes, игнорируя язык, query и fragment. Один адаптер разметки на все поддержанные ленты. MutationObserver обрабатывает добавленные карточки; WeakMap/атрибут владения предотвращает повторную вставку. Подписки очищаются при смене контекста. Неподдержанная карточка остаётся нетронутой.

Панель на React монтируется в изолированный Shadow DOM, метки — лёгкие кнопки. Это обеспечивает одинаковое поведение браузеров без разных native sidebar APIs. Стили учитывают светлую/тёмную тему; семантика, управление фокусом и клавиатура проверяются отдельно. Popup содержит только вход и настройки. Черновики панели хранятся по article ID в памяти страницы до закрытия страницы, чтобы переход между статьями не переносил чужой комментарий.

### Сеть и состояние

Все запросы клиента проходят через background WXT; content script не получает bearer token. Разрешения ограничены habr.com, собственным API, storage и identity. Background использует браузерные механизмы конкретного MV3 target; долгоживущая память background не считается надёжным хранилищем.

POST /api/articles/summary принимает до 100 уникальных ID и возвращает counts + label, включая нулевые статьи. GET /api/articles/:id/votes возвращает до 50 записей с курсором (updatedAt,id) и публичными полями. PUT /api/articles/:id/vote заменяет собственный голос, DELETE удаляет идемпотентно. Мутация возвращает актуальный агрегат и текущий голос. Сервер проверяет ID, enum, длину комментария и размеры batch; owner берётся только из сессии. Списки обновляются после мутации, старые запросы панели отсеиваются по выбранному ID/поколению запроса.

В одном документе одинаковые ID получают общий результат. Между вкладками background рассылает уведомление о собственных изменениях; внешние голоса обновляются при новом запросе/открытии панели. Не обещаем realtime. Неуспешные ответы не превращаются в нулевые агрегаты. Если свежая проверка свёрнутой статьи не удалась, карточка раскрывается и получает состояние ошибки.

### Данные и агрегация

User: internal ID, unique githubId, login, displayName, blockedAt. Session: hash случайного токена, userId, expiresAt (30 дней), revokedAt. Vote: articleId, userId, enum human/partial/ai, nullable comment, commentHiddenAt, createdAt, updatedAt; unique(articleId,userId), индекс для articleId и сортировки. Отдельная Article-таблица не нужна, пока нет собственной метаинформации: заголовок берётся из страницы и не считается доверенным HTML.

Агрегаты вычисляются SQL GROUP BY по неблокированным пользователям, без материализованных счётчиков. Красный проверяется целочисленно: ai>=3 && ai*5>=N*4. Транзакция и уникальность БД защищают upsert; агрегат мутации читается после записи в той же транзакции. Позднейшие конкурентные изменения отражаются следующим чтением. Удаление голоса действительно удаляет запись, история изменений не ведётся.

### OAuth и сессия расширения

Использовать browser.identity.launchWebAuthFlow с HTTPS backend callback и разрешённым extension redirect URL. Backend хранит короткую OAuth transaction: случайный state, GitHub PKCE verifier, разрешённый redirect и отдельный challenge клиента расширения. Backend обменивает GitHub code с PKCE и secret, получает стабильный GitHub ID, затем перенаправляет расширение с одноразовым собственным кодом (TTL 60 секунд), но без session token в URL. Background обменивает код + клиентский verifier на собственный непрозрачный session token; код одноразовый и связан с transaction. TTL OAuth transaction — 10 минут. OAuth transaction и одноразовый код хранить в PostgreSQL с атомарным потреблением; просроченные записи удалять при обращении и периодической очистке. Секретные verifier шифровать серверным ключом из окружения.

OAuth secret и provider token остаются backend; provider token после получения профиля не сохраняется. Минимальные права без доступа к репозиториям. Токен сервиса хранится в extension-origin IndexedDB, доступной background/popup, а не в page DOM или content-script-readable storage. Сервер хранит только hash токена. Logout отзывает серверную сессию до подтверждения завершения; при сетевой ошибке UI сообщает о незавершённом выходе и даёт повторить. Успех очищает локальные данные и уведомляет вкладки. state/challenges не логируются. Callback очищает URL и не загружает сторонние ресурсы.

Background принимает только известные сообщения с валидированными payload и допустимыми sender origins; не предоставляет произвольный HTTP proxy. Контроль прав выполняется сервером независимо от origin/CORS. Настроенные redirect URLs для обоих браузеров проверяются allowlist, без произвольных redirects.

### Настройки и сворачивание

Булевый collapseRed хранится в browser.storage.local; ключ отсутствует означает false. Для красной карточки CSS скрывает тело, сохраняя заголовок, метку и доступную кнопку. DOM оригинального тела не удаляется. Набор manuallyExpanded article IDs живёт в памяти страницы до reload. Обновление настройки восстанавливает карточки немедленно; изменение метки и ошибка проверки также раскрывают их.

### Минимальная защита от злоупотреблений

Fastify ограничивает body, частоту OAuth/read по IP и запись по session user ID (начальный лимит 10 записей/минуту, конфиг backend). PostgreSQL гарантирует один голос на аккаунт и статью. Комментарии только plain text. Операторская локальная CLI-команда скрывает комментарий либо блокирует user, исключая все его голоса и отзывая сессии; публичного admin API нет. Redis и отдельный модераторский UI не нужны при одном экземпляре API.

## Risks / Trade-offs

- Изменение DOM Хабра → изолированный адаптер, fixtures и проверка реальных лент в обоих браузерах; неизвестные карточки не ломать.
- Различия MV3/OAuth → ранняя загрузка обеих сборок и настоящий GitHub-вход в каждом браузере до реализации остального UI.
- Три аккаунта могут создать red → метка явно коллективная; индивидуальные голоса прозрачны, есть блокировка. GitHub не доказывает уникальность человека.
- Prisma 8 и browser targets → конкретные версии и минимальные версии браузеров фиксируются по результатам совместимости, без неподтверждённых обещаний.
- Один экземпляр API и rate limits в памяти → допустимо для первого выпуска; при горизонтальном масштабировании нужны общие ограничения.
- Изменение самой статьи не обнуляет голоса → голос относится к ID статьи, время голосования видно; версионирование текста вне scope.
- Курсор при одновременном редактировании голосов не является snapshot → refresh сбрасывает список; стабильность гарантируется при неизменных данных.

## Migration Plan

1. При apply создать workspace, локальную конфигурацию и первоначальные миграции; проверить их на пустой тестовой PostgreSQL.
2. Настроить отдельное GitHub OAuth application для разработки, HTTPS API и redirect allowlist обоих браузеров. Секреты только в окружении, в репозитории только имена переменных и примеры без значений.
3. Проверить оба пакета расширения локальной загрузкой и пройти сценарии specs; сохранить версии браузеров, команды и результаты.
4. Подготовить README запуска API/миграций/сборки и rollback. Публикация и production deploy требуют отдельного запроса.
5. Для rollback остановить новый API или вернуть предыдущий пакет и отключить/откатить расширение; пользовательские голоса и БД сохранять. Не выполнять destructive down migration. Перед будущими изменениями схемы делать проверяемую резервную копию.
